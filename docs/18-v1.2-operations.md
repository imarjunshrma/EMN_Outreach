# 18 — v1.2 operations, deployment, testing and external verification

## 1. Upgrading an existing VPS install (1.1 → 1.2)
The VPS install (systemd or PM2 + Nginx) is unchanged. Upgrade the same way as before:

```bash
# 1. Upload and unpack the new zip next to the old release, then:
cd emn-outreach-os
# 2. Add the new variables to /etc/emn/emn.env (or your .env): see section 2. All are optional.
# 3. Deploy: backs up the DB, runs migrations + SQL guards, builds, restarts api/worker/web
sudo bash scripts/deploy.sh                      # or: sudo PROCESS_MANAGER=pm2 bash scripts/deploy.sh
# 4. Reload Nginx (rate limits now cover 2FA verify and the billing webhooks)
sudo cp deployment/nginx/emn.conf /etc/nginx/sites-available/emn.conf   # re-apply your server_name/TLS edits
sudo nginx -t && sudo systemctl reload nginx
bash scripts/healthcheck.sh
```

**Migration** `20261121090000_v1_2_security_ai_workflows_billing` is additive: new tables, new nullable or defaulted columns, and new enum values. It has no DROPs and no type changes. It was verified three ways:
- on a fresh database,
- on the existing development database (`No pending migrations` afterwards),
- on a database at v1.1 containing rows, upgraded to v1.2 with data intact.

`deploy.sh` takes a database backup before migrating. Rollback is `scripts/restore.sh` plus the previous release.

The worker registers new schedules by itself:
- `domain-renewals`: 04:07 UTC
- `workflow-daily`: 06:11 UTC
- `reports-daily`: 07:29 UTC

## 2. New environment variables (all optional)
| Variable | Needed for | Without it |
|---|---|---|
| `SYSTEM_SMTP_URL`, `SYSTEM_MAIL_FROM` | Password-reset emails, 2FA notices, scheduled reports, email alert channels | Password reset still answers normally but **no email is sent**; reports record "System email not configured"; the CLI `npm run reset-password` still works |
| `BILLING_ENABLED` | SaaS plans and limits | `false` (default) = self-hosted: unlimited, nothing enforced |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | Card checkout / portal | Checkout returns `PROVIDER_NOT_CONFIGURED` |
| `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET` | India subscriptions | same |

Provider keys for ZeroBounce, NeverBounce, Hunter and Cloudflare are entered in the app under **Integrations**. They are stored encrypted.

### Billing setup (only when `BILLING_ENABLED=true`)
1. Create a product with monthly and yearly prices in Stripe, and/or plans in Razorpay.
2. Store the IDs on each plan (one-off SQL; the plans are seeded on first use):
   ```sql
   UPDATE "Plan" SET "providerPriceIds" = '{"stripe_month":"price_…","stripe_year":"price_…","razorpay_month":"plan_…"}' WHERE code = 'growth';
   ```
3. Add the webhook endpoints:
   - Stripe: `https://<host>/api/v1/webhooks/billing/stripe`
   - Razorpay: `https://<host>/api/v1/webhooks/billing/razorpay`

   The event lists are in `.env.example`.
4. Platform admins (the first user) can override plan, status or trial at `/admin`.

## 3. Docker (optional alternative)
`docker-compose.yml` runs Postgres, Redis, a one-shot `migrate` job, `api`, `worker` and `web`. All env comes from `.env`, so the v1.2 variables flow through unchanged.
```bash
cp .env.example .env   # fill SESSION_SECRET, ENCRYPTION_KEYS, POSTGRES_PASSWORD, REDIS_PASSWORD, APP_URL …
docker compose build && docker compose up -d
```
`docker compose config` validates. **The images were not built in the build environment** because Docker Hub is blocked there. Build them once on your server before relying on Docker. The VPS path does not need Docker.

## 5. Live provider verification (`npm run live-check`)
Fakes and protocol tests prove the logic. Only a live run proves an account works. The harness:
- uses the production adapters,
- reads credentials from `LIVE_*` and the existing env vars,
- never prints secrets,
- emails only `LIVE_SEND_TO`,
- creates no DNS records and charges nothing,
- writes `live-check-report.json`.

```bash
# keep these in an untracked file, e.g. ~/emn-live.env, then:  set -a; . ~/emn-live.env; set +a
LIVE_CHECK=1 npm run live-check                       # read-only
LIVE_CHECK=1 LIVE_SEND_TO=you@yourdomain.com npm run live-check   # also sends one test email per mailbox
```
| Provider | Variables |
|---|---|
| Gmail | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `LIVE_GMAIL_REFRESH_TOKEN`, `LIVE_GMAIL_ADDRESS` (a **test** mailbox, not the EMN business mailbox) |
| Microsoft 365 | `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, `MICROSOFT_TENANT`, `LIVE_MS_REFRESH_TOKEN`, `LIVE_MS_ADDRESS` |
| SMTP + IMAP | `LIVE_SMTP_HOST`, `LIVE_SMTP_PORT`, `LIVE_SMTP_SECURE`, `LIVE_IMAP_HOST`, `LIVE_IMAP_PORT`, `LIVE_IMAP_SECURE`, `LIVE_MAIL_USER`, `LIVE_MAIL_PASSWORD`, `LIVE_MAIL_ADDRESS` |
| System mailer | `SYSTEM_SMTP_URL` |
| AI | `LIVE_ANTHROPIC_KEY` (+`LIVE_ANTHROPIC_MODEL`), `LIVE_OPENAI_KEY` (+`LIVE_OPENAI_MODEL`) |
| Verifiers / finder | `LIVE_MILLIONVERIFIER_KEY`, `LIVE_ZEROBOUNCE_KEY`, `LIVE_NEVERBOUNCE_KEY`, `LIVE_HUNTER_KEY`, `LIVE_VERIFY_EMAIL` |
| Cloudflare (read-only) | `LIVE_CLOUDFLARE_TOKEN`, `LIVE_CLOUDFLARE_DOMAIN` |
| Stripe / Razorpay (read-only) | `STRIPE_SECRET_KEY` (+webhook secret), `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET` |
| S3 | `S3_BUCKET`, `S3_REGION`, `S3_ENDPOINT`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` |

A refresh token for a test mailbox can be obtained by connecting it in the app once. Alternatively use the provider's OAuth playground with the same client ID and scopes.

**Status in this build:** the harness ran with no credentials, and every provider reported `skipped`. **No provider has been live-verified here.**

## 6. Still requires credentials or external verification
1. **Gmail API**: send, sync, thread matching and revocation against a real Google Workspace test mailbox. Also Google OAuth app verification for the `gmail.send`/`gmail.readonly` scopes if used outside your own Workspace.
2. **Microsoft Graph**: send, delta sync and change notifications (needs public HTTPS) against a real M365 test mailbox. Entra app consent.
3. **IMAP**: real server login and sync (SMTP is protocol-tested in-process; IMAP is not).
4. **System SMTP** for reset emails, reports and email alerts.
5. **Stripe and Razorpay**:
   - live or test-mode checkout, portal and webhooks (signature verification is unit-tested with the documented algorithms);
   - price IDs on plans;
   - tax/GST configuration in the gateway dashboards.
6. **ZeroBounce, NeverBounce, Hunter, MillionVerifier, Apollo, Brave/Serper**: real API keys. Response-field mappings follow the public docs and should be confirmed with live-check.
7. **Cloudflare DNS write**: create one record on a test zone from the domain page.
8. **Slack incoming webhook**: send a test from Reports & alerts.
9. **S3/R2/B2 bucket**: live-check S3 section.
10. **Docker images**: `docker compose build` on a host with registry access.
11. **AI providers**: real keys; output quality of Copilot and reply drafts should be reviewed by a person before relying on them.
