# Tenant isolation design

Isolation is enforced independently at each layer, so a bug in one layer is caught by the next.

## 1. Request layer (API)

- `backend/src/http/middleware.ts` authenticates a session cookie or an API key. API keys carry exactly one `workspaceId`.
- `backend/src/http/router.ts` has five auth modes. For `workspace` routes it calls `resolveMembership(workspaceId)`, which returns a role only if **(a)** a `WorkspaceMember` row exists, **(b)** the caller is OWNER/ADMIN of that workspace's own organization, or **(c)** the caller is platform staff with an unexpired, unrevoked support grant for that organization (then VIEWER, read-only, each request audited). Anything else is `404 NOT_FOUND`.
- For `org` routes, an `OrganizationMember` row for `(organizationId, userId)` is required; API keys are rejected.
- For `platform` routes, `User.platformRole` must hold the route's permission; everyone else gets 404.
- The resolved `workspaceId`/`organizationId` are put on the handler context. Handlers never read a tenant id from the body.
- Tenant status gate: read-only for SUSPENDED/CANCELLED, closed for DELETION_PENDING/DELETED, with explicit `allowWhenInactive` exceptions (billing, export, usage, deletion cancel).

## 2. Query layer (services)

Every service function takes `workspaceId` (or `organizationId`) as its first argument and includes it in every `where` clause, e.g. `findFirst({ where: { id, workspaceId } })`. Updates and deletes on a single id first load with the scoped `findFirst`, or use `updateMany/deleteMany` with the scope. Exports (`ops.workspaceExport`, org export) iterate only the organization's workspaces.

## 3. Database layer

`prisma/sql/002_tenant_guards.sql` (generated by `scripts/generate-tenant-guards.ts`, freshness checked by `tests/unit/tenant-guards.test.ts`):

- `emn_same_workspace(col, table, …)` — a `BEFORE INSERT OR UPDATE` trigger on 40 tables covering 72 foreign keys. It refuses a row whose referenced record belongs to another workspace (e.g. a `CampaignList` joining a campaign of workspace A to a list of workspace B).
- `emn_workspace_org_immutable` — `Workspace.organizationId` can never change, so data cannot be moved between tenants.
- `emn_append_only` — `PlatformAuditEvent` cannot be updated or deleted (except inside the purge path, which sets a transaction-local flag); `OrganizationStatusChange` cannot be updated.
- Composite uniqueness: `(workspaceId, emailNormalized)` on leads, `(organizationId, userId)` on members, `(organizationId, idempotencyKey)` on usage events, `(organizationId, metric, periodStart)` on counters.

**RLS is not used** (see the assessment); we do not claim it.

## 4. Cache and Redis

| Key | Scope |
|---|---|
| `rl:tenant:<organizationId>:api:<minute>` | Organization API throughput |
| `tenant:slots:<organizationId>:<queue>` | Fair-share job slots |
| `rl:<method>:<path>:<ip|userId|workspaceId>` | Route rate limits |
| `events:<workspaceId>` | Realtime channel; the SSE endpoint is a `workspace` route, so subscribers are members |
| `lock:*`, `oauth:state:*`, `totp:*` | Keyed by globally unique ids |

No tenant data is cached in Redis.

## 5. Queues and workers

- Every tenant job payload carries `workspaceId`, set by the server from the request context.
- Handlers load records with `where: { id, workspaceId }`, so a forged id from another workspace finds nothing.
- `tenantGate` (worker) resolves the organization from the workspace before every job; cost-incurring or outbound jobs (AI, research, personalization, verification, imports, workflow runs, replies, webhooks, channel notifications) are **skipped** when the tenant is not operational. Sending is gated inside the engine, which defers instead of dropping. Compliance work (privacy export/erasure, mailbox sync that records unsubscribes) continues.
- `acquireSlot` limits each organization to `TENANT_JOB_SLOTS` concurrent heavy jobs (AI, research, personalize, verify, import); excess jobs are delayed, not failed.

## 6. Storage

Object keys are `<workspaceId>/…`. `assertKeyBelongsTo(workspaceId, key)` is checked before reads; files are only served through authenticated workspace routes (no public bucket URLs). Purging a tenant calls `deletePrefix(workspaceId)` for each workspace (local disk and S3 adapters).

## 7. Integrations and credentials

Every provider credential (`Integration`, `EmailAccount`, `AiProvider`, DNS tokens) is stored per workspace, encrypted with AES-256-GCM, and loaded with the workspace scope. Platform-level credentials (Stripe/Razorpay keys, system SMTP, OAuth client ids) live only in the environment and are never stored per tenant. Platform tenant detail shows integration **status only**.
